The Big Picture

Three separate tools are working together every time you run your app. Understanding which one is responsible for what prevents 90% of confusing errors.

🔨 Gradle
Build tool — manages dependencies, compiles code, runs tests, packages the JAR. Knows nothing about Spring.
☕ JVM
Runtime — loads `.class` bytecode, manages memory (heap/GC), runs threads. Knows nothing about Gradle or Spring.
🌱 Spring Boot
Application framework — scans your code for annotations, wires beans together, starts an embedded web server. Runs inside the JVM.
Key insight

Gradle runs before your application. It produces a JAR file, then exits. Spring Boot runs inside the JVM, started by the JVM reading that JAR. They never run at the same time.

Gradle

What is Gradle?

Gradle is a build automation tool. It's a program that runs on your machine (not in production) and performs the steps needed to turn your source code into a running program.

build.gradle — the build script

This is a Groovy (or Kotlin) script that Gradle executes to understand your project.

api-service/build.gradle — annotated
plugins {
    // Adds Spring Boot tasks: bootRun, bootJar, bootBuildImage
    id 'org.springframework.boot' version '3.3.5'
    // Imports Spring's BOM — pins all dep versions so you don't specify them
    id 'io.spring.dependency-management' version '1.1.4'
    id 'java'           // Adds: compileJava, test, jar tasks
}

java {
    sourceCompatibility = JavaVersion.VERSION_21   // Must compile to Java 21 bytecode
}

dependencies {
    // "implementation" = needed at compile + runtime, not exposed to modules that depend on us
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
    implementation 'org.springframework.boot:spring-boot-starter-amqp'  // RabbitMQ

    // "runtimeOnly" = only needed at runtime, not during compilation
    runtimeOnly 'org.postgresql:postgresql'

    // "testImplementation" = only on the test classpath
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}
Why no version numbers?

The io.spring.dependency-management plugin imports Spring Boot's Bill of Materials (BOM). This is a curated list of thousands of library versions that are guaranteed to work together. Omitting the version means "use whatever Spring Boot says is compatible."

Incremental compilation — why rebuilds are fast

Gradle tracks the inputs and outputs of every task. If AuthController.java hasn't changed since last run, compileJava shows UP-TO-DATE and is skipped entirely. This is why a second ./gradlew test runs in 3 seconds when the first took 2 minutes.

The fat JAR — how it works

A standard JAR only contains your code. A Spring Boot fat JAR (built by bootJar) contains:

Java Compilation

Source → Bytecode

Java is a compiled language. Your .java source files are not executed directly — they're translated into an intermediate form called bytecode first.

  1. You write NotificationController.java
    Human-readable Java source with annotations, generics, and method bodies.
  2. Gradle invokes javac (the Java compiler)
    javac parses the source, resolves types against the classpath JARs, performs type checking, and generates bytecode.
  3. Output: NotificationController.class
    A binary file containing JVM instructions — not machine code, but a portable intermediate format. One .java file → one or more .class files (inner classes get their own files).
  4. Annotation processing happens during compilation
    Lombok's @Getter, @RequiredArgsConstructor etc. are processed by the Java annotation processor before javac compiles the class. Lombok generates the boilerplate Java source, then javac compiles it.
Annotation processing — what Lombok actually generates
// What you write:
@Getter @RequiredArgsConstructor
public class NotificationService {
    private final NotificationRepository repo;
}

// What javac actually compiles (Lombok generated this):
public class NotificationService {
    private final NotificationRepository repo;

    public NotificationRepository getRepo() { return this.repo; }

    public NotificationService(NotificationRepository repo) {
        this.repo = repo;
    }
}
Java Compilation

JVM & Class Loading

The JVM is a virtual machine — it executes bytecode the same way regardless of the underlying OS or hardware. Class loading is how bytecode gets from the JAR file into executable memory.

The ClassLoader hierarchy

Bootstrap ClassLoader
Loads Java's core classes (java.lang.*, java.util.*). Part of the JVM itself, written in native code.
Platform ClassLoader
Loads Java SE platform APIs (Java 9+ module system). Previously called Extension ClassLoader.
Application ClassLoader
Loads your application's classes from the classpath. Normally the last stop.
Spring's LaunchedURLClassLoader
Spring Boot's custom ClassLoader. Knows how to read classes from JARs nested inside your fat JAR. This is why java -jar works without unpacking.

Lazy loading

Classes are not loaded at startup — they're loaded the first time they're referenced. This is why Spring's context initialization log shows classes being scanned: Spring forces each bean class to load so it can inspect its annotations.

JIT — Why Java Gets Faster Over Time

The JVM starts by interpreting bytecode (slow), but watches which methods are called most often. Hot methods get Just-in-Time compiled by the JIT compiler to native machine code (fast). This is why Java apps sometimes feel slow for the first few requests.

Spring Boot

The Boot Process — What Happens in 12 Seconds

When ./gradlew :api-service:bootRun starts, Spring Boot runs through a fixed startup sequence before your first request can be served.

  1. JVM starts — main() called
    ApiServiceApplication.main() calls SpringApplication.run(). This is the single entry point into Spring.
  2. ApplicationContext created
    Spring creates a AnnotationConfigServletWebServerApplicationContext — the container that will hold every bean. Think of it as a giant Map of name → bean instance.
  3. Auto-configuration loads
    Spring reads META-INF/spring/AutoConfiguration.imports from every JAR on the classpath and evaluates which auto-configs apply based on what's present (see next section).
  4. Component scan
    Spring scans the package com.tinniestudio.api and finds every class annotated with @Component, @Service, @Repository, @Controller, @RestController, @Configuration.
  5. Beans instantiated and wired
    Spring creates one instance of each bean. Constructor arguments are resolved by type — this is dependency injection. @RequiredArgsConstructor + Lombok = Spring injects via the generated constructor.
  6. Flyway runs
    The Flyway bean runs all pending migrations (V1 through V42) in order before any request can be served. The DB schema is guaranteed correct before the app accepts traffic.
  7. Embedded Tomcat starts on port 8080
    Spring starts Tomcat, registers the DispatcherServlet, and the app is ready. Also starts management server on port 8081.
ApiServiceApplication.java
@SpringBootApplication   // This one annotation does 3 things:
public class ApiServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(ApiServiceApplication.class, args);
    }
}

// @SpringBootApplication expands to:
@Configuration        // This class can define @Bean methods
@ComponentScan        // Scan this package + sub-packages for components
@EnableAutoConfiguration  // Load matching auto-configurations from JARs
Spring Boot

Auto-Configuration — The "Magic"

Auto-configuration is how Spring Boot avoids pages of XML config. It's based on a simple idea: if a class exists on the classpath, configure a bean for it automatically.

The mechanism is @ConditionalOn* annotations on auto-config classes:

How DataSource auto-config works (simplified)
@Configuration
@ConditionalOnClass(DataSource.class)    // Only if DataSource is on classpath
@ConditionalOnMissingBean(DataSource.class) // Only if YOU haven't already defined one
public class DataSourceAutoConfiguration {

    @Bean
    @ConfigurationProperties("spring.datasource")  // Reads from application.yml
    public HikariDataSource dataSource() {
        return DataSourceBuilder.create()
            .type(HikariDataSource.class).build();
    }
}

You added spring-boot-starter-data-jpa → it brings DataSource.class onto the classpath → DataSourceAutoConfiguration fires → a connection pool to Postgres is created automatically, configured by your application.yml.

Spring Boot

Bean Lifecycle — Dependency Injection

A bean is an object whose lifecycle is managed by Spring. Spring creates it, injects its dependencies, and (if needed) destroys it on shutdown.

How NotificationServiceImpl gets wired — traced end to end
// 1. You declare the class as a @Service component
@Service
@RequiredArgsConstructor
public class NotificationServiceImpl implements NotificationService {

    // 2. Spring sees these final fields — it needs to provide them
    private final NotificationRepository       notifRepo;
    private final NotificationTemplateRepository templateRepo;
    private final NotificationPreferenceRepository prefRepo;
}

// 3. Spring finds NotificationRepository (a JPA repo interface)
public interface NotificationRepository
    extends JpaRepository<Notification, UUID> { }
// Spring Data JPA auto-generates a proxy class implementing this interface
// and registers it as a bean — no @Repository annotation needed

// 4. When Spring creates NotificationServiceImpl, Lombok's generated
//    constructor is called with the resolved beans:
new NotificationServiceImpl(notifRepoBean, templateRepoBean, prefRepoBean);

// 5. NotificationController declares it needs the service:
@RestController
@RequiredArgsConstructor
public class NotificationController {
    private final NotificationService notificationService;
    // Spring injects the NotificationServiceImpl bean here
}
Interface, not implementation

NotificationController depends on NotificationService (the interface), not NotificationServiceImpl. Spring looks for a bean that implements that interface and injects it. This is why tests can inject a @MockBean NotificationService — the mock also implements the interface.

Spring Boot

Web Layer — From HTTP Request to Response

Every HTTP request passes through a chain of components before reaching your controller method.

Tomcat / HTTP
Accepts TCP connection, parses raw HTTP bytes into a HttpServletRequest object.
SecurityFilterChain
Your JwtAuthenticationFilter runs here — extracts JWT from header, validates it, sets SecurityContextHolder with the user's identity. If invalid: returns 401 before hitting any controller.
RateLimitAspect
@RateLimit annotations are enforced here via AOP (Aspect-Oriented Programming). Checks Redis for the request count for this IP/user in the current window.
DispatcherServlet
Spring's front controller. Looks up which @RequestMapping method matches the URL and HTTP method. Routes to the correct controller.
Your @RestController method
Your actual code runs here. Arguments are resolved (@PathVariable, @RequestBody → deserialized via Jackson, @AuthenticationPrincipal → from SecurityContext).
SuccessResponseWrapper
Your ResponseBodyAdvice intercepts the return value and wraps it: { success: true, message: "...", data: <your object> }. Jackson then serializes this to JSON.
Tomcat writes response
JSON bytes written to the TCP socket. Request complete.
Tracing GET /notifications through the chain
// 1. JWT filter extracts userId from token → sets principal
// 2. Dispatcher finds this method:
@GetMapping  // → matches GET /notifications
public ResponseEntity<Page<NotificationResponse>> list(
    @AuthenticationPrincipal UserDetails principal,   // from SecurityContext
    @PageableDefault(size = 20) Pageable pageable       // from ?page=0&size=10
) {
    return ResponseEntity.ok(
        notificationService.listForUser(
            UUID.fromString(principal.getUsername()), pageable
        )
    );
}
// 3. Return value → SuccessResponseWrapper wraps it
// 4. Jackson serializes → {"success":true,"data":{"content":[...],"totalElements":5}}
TinnieStudio Layer

Security — How Auth Works

JWT Spring Security UserDetails @PreAuthorize

Authentication uses stateless JWTs. The server issues a signed token at login; every subsequent request must present it. The server never stores session state in memory.

Token validation flow in JwtAuthenticationFilter
// Runs on EVERY request (it's a OncePerRequestFilter)
protected void doFilterInternal(HttpServletRequest request, ...) {
    String token = extractBearerToken(request);  // from Authorization header
    if (token != null && jwtProvider.isValid(token)) {
        UUID userId = jwtProvider.getUserId(token);
        UserDetails user = userDetailsService.loadUserById(userId);
        // Puts identity into SecurityContext — available for the whole request
        SecurityContextHolder.getContext().setAuthentication(
            new UsernamePasswordAuthenticationToken(user, null, user.getAuthorities())
        );
    }
    filterChain.doFilter(request, response);  // continue to next filter/controller
}

The @PreAuthorize annotation on controllers checks the SecurityContext after the filter runs. hasRole('ADMIN') checks whether the user's GrantedAuthority list contains ROLE_ADMIN.

TinnieStudio Layer

JPA + Flyway — Database Layer

Flyway Hibernate ORM HikariCP Spring Data JPA

Three distinct tools handle database access, each with a different responsibility:

HikariCP

Connection pool. Opens N physical connections to PostgreSQL and reuses them. Configured via spring.datasource.* in application.yml. Prevents the overhead of creating a new TCP connection for every query.

Flyway

Schema versioning. Runs V1__*.sql through V42__*.sql in order, tracking which have run in flyway_schema_history. Only runs pending migrations. Guarantees your schema is always in a known state before the app serves requests.

Hibernate/JPA

Object-Relational Mapper. Translates between your @Entity Java objects and SQL rows. Generates SELECT/INSERT/UPDATE statements from JPQL or method names like findByUserId. ddl-auto: none means Hibernate does not touch the schema — Flyway owns it.

Spring Data JPA

Interface magic. You write interface NotificationRepository extends JpaRepository<Notification, UUID>. Spring Data generates a proxy class at startup that implements every method — no boilerplate SQL needed.

How findByUserIdOrderByCreatedAtDesc is auto-implemented
// You write only this interface method signature:
Page<Notification> findByUserIdOrderByCreatedAtDesc(UUID userId, Pageable pageable);

// Spring Data generates this SQL at startup (via reflection on the method name):
SELECT * FROM notifications
WHERE user_id = ?
ORDER BY created_at DESC
LIMIT ? OFFSET ?

Why the RabbitMQ errors on local bootRun?

Spring AMQP's listener containers start immediately and try to connect to localhost:5672. Without a broker running locally, they log Connection refused and retry every 30 seconds. The app still starts and serves HTTP — RabbitMQ is only needed for async message processing, not for the API itself.

TinnieStudio Layer

Redis — Caching & Rate Limiting

Redis is used for two distinct purposes in TinnieStudio, both backed by the same Redis server:

Response Caching

Spring's @Cacheable annotation stores method return values in Redis with a TTL. Next call with same args → return from Redis, skip DB query. Used for category lists, subscription plans — data that changes rarely.

Rate Limiting

@RateLimit uses Redis sliding-window counters. For each request, a key like ratelimit:USER_OR_IP:userId:endpoint is incremented in Redis. If count exceeds maxRequests in the window → 429 Too Many Requests returned before the controller is even called.

Rate limit check — behind the @RateLimit annotation
// RateLimitAspect intercepts methods annotated with @RateLimit
// Before the method runs:
String key = "ratelimit:" + strategy + ":" + identifier + ":" + endpoint;
Long count = redisTemplate.opsForValue().increment(key);
if (count == 1) {
    redisTemplate.expire(key, windowMinutes, TimeUnit.MINUTES);  // set TTL on first hit
}
if (count > annotation.maxRequests()) {
    throw new TooManyRequestsException(annotation.errorMessage());
}
// method proceeds normally if count is within limit
TinnieStudio Layer

Scheduled Jobs — ShedLock

Spring's @Scheduled fires a method on a timer. But in a multi-instance deployment, all instances fire at the same time — causing duplicate runs. ShedLock prevents this using a database lock.

How ShedLock prevents duplicate job runs
@Scheduled(cron = "0 0 2 * * *")       // Fire at 02:00 UTC daily
@SchedulerLock(name = "NotificationCleanupJob",
    lockAtMostFor = "5m", lockAtLeastFor = "1m")
@Transactional
public void run() { ... }

/*  When the cron fires across 3 running instances:
    Instance A: INSERT INTO shedlock(name='NotificationCleanupJob', ...) ← wins
    Instance B: INSERT fails (row exists) → skips job ← lock prevents double-run
    Instance C: INSERT fails → skips job

    After lockAtMostFor expires, the row is available again for the next run.
    lockAtLeastFor prevents re-run even if instance A finishes quickly.
*/

Testing Architecture

TinnieStudio uses two testing patterns, each loading a different slice of the application.

@WebMvcTest — controller layer only

Loads only the web layer: your controller, Spring MVC config, and Jackson. No database, no real services.

NotificationControllerTest.java — annotated
@WebMvcTest(controllers = NotificationController.class)
// ↑ Loads ONLY NotificationController and MVC infrastructure.
//   Does NOT start the full Spring context, Flyway, or DB.
@AutoConfigureMockMvc(addFilters = false)
// ↑ Disables the SecurityFilterChain so tests don't need real JWTs
class NotificationControllerTest {

    @Autowired MockMvc mockMvc;
    // ↑ Fake HTTP client — fires requests directly into the DispatcherServlet
    //   without a real network connection or Tomcat

    @MockBean NotificationService notificationService;
    // ↑ Replaces the real NotificationService with a Mockito mock.
    //   The controller gets injected with THIS mock, not the real impl.

    @MockBean JwtTokenProvider jwtTokenProvider;
    @MockBean JwtAuthenticationFilter jwtAuthFilter;
    // ↑ Required because WebMvcTest still tries to load security beans.
    //   Mocking them prevents "No bean of type JwtTokenProvider found" errors.

    @Test
    @WithMockUser(username = "00000000-0000-0000-0000-000000000002")
    // ↑ Injects a fake SecurityContext so @AuthenticationPrincipal works
    void unreadCount_returns200() throws Exception {
        when(notificationService.getUnreadCount(any())).thenReturn(3L);
        // ↑ Tell the mock: when this method is called (with any arg), return 3

        mockMvc.perform(get("/notifications/unread-count"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.data.count").value(3));
        // ↑ $.data.count — because SuccessResponseWrapper wraps: {success, data, message}
    }
}
